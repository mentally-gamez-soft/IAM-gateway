# Task 006-2 — Add Deprecation Headers to Legacy Routes

## Parent User Story

[US-006 — API Versioning Strategy](../USER_STORIES/user_story_006.md)

## Description

Maintain temporary backward-compatible unversioned routes (e.g., `/signup`, `/login`) with HTTP `Deprecation` headers to warn API consumers about the migration.

## Work to be Done

1. Create a separate blueprint `legacy_bp` for unversioned routes
2. Register legacy routes that proxy to the versioned handlers:
   - `/signup` → `/api/v1/signup`
   - `/login` → `/api/v1/login`
   - `/logout` → `/api/v1/logout`
   - `/confirm/<token>` → `/api/v1/confirm/<token>`
   - `/role/add` → `/api/v1/role/add`
3. Add HTTP headers to all legacy route responses:
   - `Deprecation: true`
   - `Sunset: <date>` (e.g., 6 months from now)
   - `Link: </api/v1/...>; rel="successor-version"`
4. Log a warning on each legacy route access
5. Document the deprecation timeline

## Expected Outcome

- Existing clients continue to work with unversioned routes
- Clients are warned via HTTP headers to migrate to versioned routes
- Deprecation is logged for monitoring

## Priority

**High**

## Acceptance Criteria

- [ ] Legacy routes still return correct responses
- [ ] `Deprecation` header is present in legacy route responses
- [ ] `Sunset` header indicates the planned removal date
- [ ] `Link` header points to the versioned successor endpoint
- [ ] A warning log is emitted on each legacy route access
- [ ] Legacy blueprint can be removed cleanly when deprecation period ends
