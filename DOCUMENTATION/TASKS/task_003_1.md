# Task 003-1 — Design and Create RefreshToken Model

## Parent User Story

[US-003 — Refresh Token Mechanism](../USER_STORIES/user_story_003.md)

## Description

Design and implement a `RefreshToken` database model to securely store refresh tokens with support for rotation, revocation, and token family tracking.

## Work to be Done

1. Create the `RefreshToken` model in `core/users/models.py` with fields:
   - `id` (Integer, PK)
   - `token` (String, unique, not null) — hashed refresh token
   - `user_id` (UUID, FK to `gw_user.id`, not null)
   - `family_id` (UUID) — groups tokens from the same login session for reuse detection
   - `created_on` (DateTime, not null)
   - `expires_on` (DateTime, not null)
   - `revoked` (Boolean, default False)
   - `revoked_on` (DateTime, nullable)
   - `replaced_by` (String, nullable) — hash of the new token that replaced this one
2. Add CRUD methods: `create()`, `revoke()`, `is_expired()`, `is_valid()`
3. Add class methods: `get_by_token()`, `revoke_all_for_user()`, `revoke_family()`
4. Generate Alembic migration
5. Add relationship to `GwUser` model

## Expected Outcome

- `RefreshToken` model exists with all required fields and methods
- Migration applies cleanly
- Token family tracking enables reuse detection

## Priority

**High**

## Acceptance Criteria

- [ ] Model schema matches the specification above
- [ ] Alembic migration created and tested (up/down)
- [ ] `is_valid()` checks both `revoked` and `expires_on`
- [ ] `revoke_family()` revokes all tokens sharing the same `family_id`
- [ ] `revoke_all_for_user()` revokes all tokens for a given user
- [ ] Relationship with `GwUser` is correctly defined
